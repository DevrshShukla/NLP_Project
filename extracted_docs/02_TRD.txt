1. Technical Overview
Study Topic Extractor is a three-tier web application: a Next.js frontend, a stateless FastAPI backend
that hosts the NLP pipeline, and (from Phase 2) a Supabase-managed PostgreSQL database with Auth
and Storage. The MVP is stateless: no database, no accounts, no server-side persistence of user
content.
1.1 Architecture Principles
  Explainable first: classical NLP (spaCy, TF-IDF, n-grams) is the core; embeddings and LLMs
augment it.
 Deterministic by default: identical input, configuration and pipeline_version produce identical
output.
 Stateless API: any instance can serve any request; state lives in the DB or the client.
 Modular services: each pipeline stage is one module with typed inputs and outputs.
 Privacy by design: process in memory, never log document text, delete temporary data.
 Optional heavy dependencies: Sentence Transformers, OCR and LLMs are behind feature flags.

3. Frontend Architecture
  Routing: / landing, /analyze, /results/[analysisId], /focus/[analysisId] (P2), /history (P2),
/dashboard (P2), /settings, /login (P2).
 State: React state + Context for theme and settings; TanStack Query for API calls (retry, cache,
loading states).
 MVP result persistence: result JSON kept in sessionStorage keyed by analysisId; cleared when the
tab closes. Nothing is stored server-side.
 API client: single lib/api.ts generated types from OpenAPI (openapi-typescript) so frontend and
backend contracts stay synchronized.
 Components: presentational components under components/ui; feature components under
components/analyze|results|graph|focus.
 Theming: CSS variables defined in styles/tokens.css; data-theme="light|dark" on <html>; system
preference default.
 Accessibility: semantic HTML, focus management on route change, aria-live regions for
processing status.

4. Backend Architecture
FastAPI application with routers, dependency-injected services, and a pipeline orchestrator. CPU-bound
NLP work runs in a thread pool (run_in_threadpool) so the event loop remains responsive. Models
(spaCy, MiniLM) load once during the application lifespan and are shared read-only.

4.1 Layer Rules
  Routes validate input (Pydantic), call one service function, map exceptions to the error format. No
business logic in routes.
 Services are pure where possible: text in, structured data out; no HTTP or DB imports in NLP
modules.
 Repositories are the only code that touches the database; every query takes user_id.
 Configuration is read once from environment (pydantic-settings); no hard-coded thresholds or
weights (config.py defaults).

8. Authentication and Authorization Architecture
  MVP: no authentication. Endpoints are stateless and rate limited by IP.
 Phase 2: Supabase Auth issues JWTs; frontend uses @supabase/ssr; backend verifies the JWT
signature and expiry (sub = user id) in a get_current_user dependency.
 Authorization: ownership enforced in repositories (WHERE user_id = :uid) and by Postgres RLS as
defense in depth.
 Optional auth: /api/upload and /api/analyze remain usable anonymously; supplying a valid token
plus save=true persists results.

All errors use one envelope: {"error": {"code", "message", "details", "request_id"}}. Domain
exceptions (AppError subclasses) carry a code and HTTP status; a global handler converts them.
Unhandled exceptions become PROCESSING_FAILED (500) with a request_id; stack traces go to logs only.

10.2 Logging
  Structured JSON logs (structlog): timestamp, level, request_id, route, status, latency_ms,
char_count, page_count, error_code.
 Never log document text, extracted text, filenames of user documents, tokens, or API keys.
 Request ID generated per request, returned in X-Request-ID.
10.3 Monitoring
  Uptime check on GET /api/health (returns model-loaded status and version).
 Render/Railway metrics for CPU, memory, restarts; alert when memory > 85%.
 Optional Sentry with request bodies scrubbed (send_default_pii=false, before_send strips bodies).
 Pipeline stage timings recorded in stats.processing_ms and per-stage debug logs.

11. Caching, Performance, Scalability
11.1 Caching
  Model objects cached at startup (spaCy, MiniLM, background IDF table).
 Result cache: in-process LRU keyed by sha256(normalized_text) + sha256(config); memory-only for
privacy. Redis is optional in Phase 2 for multi-instance sharing.
 Frontend: TanStack Query cache for document lists; static assets on Vercel CDN.

11.3 Scalability Path
 1. Horizontal scaling: stateless API behind the host load balancer.
2. Background processing: FastAPI BackgroundTasks first; then Redis + RQ/Celery worker for large
documents.
3. Model isolation: move embeddings to a dedicated worker or inference service if memory pressure
grows.
4. Multilingual: language detection stage plus per-language spaCy model registry (LANG_MODELS).
5. Database: indexes and partitioning of topics by analysis_run_id if volume grows.
DEPLOYMENT CONSTRAINT. Sentence Transformers pull in PyTorch. Use the CPU-only wheel, load the
model once, and provision at least 1 GB RAM (2 GB recommended) for Phase 2 backends. The MVP
backend (no torch) fits in 512 MB.

12. Security Architecture Summary
Security is specified in detail in the Security Specification. Architectural highlights: TLS everywhere;
CORS allow-list; file validation by extension, MIME and magic bytes; size and page limits; rate limiting;
JWT verification; RLS; private storage; no content logging; secrets only in environment variables;
prompt-injection isolation for optional LLM calls.
