1. Scope and Principles
The database is Phase 2. The MVP has no database: results live in the client session and the server
keeps only an in-memory cache. This schema is designed now so the MVP result JSON maps cleanly
onto it later, and so the schema supports every Phase 2 feature.
  PostgreSQL 15 on Supabase; migrations with Alembic; SQLAlchemy 2.0 models mirror this
document exactly.
 UUID primary keys (gen_random_uuid()), timestamptz timestamps in UTC, snake_case names.
 Deleting a document or user cascades to all derived data (privacy requirement).
 The backend enforces ownership in code; Row Level Security is enabled as defense in depth.
 Analysis output is immutable: re-analysis creates a new analysis_runs row.

5. Constraints, Triggers, and Cascading
  All CHECK constraints listed in the table definitions are created in the initial migration.
 set_updated_at() trigger on users and documents.
 Deleting a documents row deletes: sections, runs (and therefore topics, keywords, clusters,
relationships, questions) and sessions. The API also deletes the Storage object; if storage deletion
fails the row is still deleted and the object key is queued in a storage_cleanup log for retry.
 Deleting a user (DELETE /api/me) deletes the profile, which cascades to everything owned; then the
Supabase auth user and the user's Storage prefix {user_id}/ are removed.
 The application layer enforces max 200 documents per user (configurable) to control storage use.

6. Row Level Security
RLS is enabled on every table. The FastAPI backend connects with a server-side role and enforces
ownership in its repository layer (every query includes user_id). RLS policies protect against any direct
access using the public anon key or a user JWT.
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
CREATE POLICY documents_owner ON documents
  FOR ALL TO authenticated
  USING (user_id = auth.uid()) WITH CHECK (user_id = auth.uid());
-- Child tables inherit ownership through the document:
ALTER TABLE topics ENABLE ROW LEVEL SECURITY;
CREATE POLICY topics_owner ON topics FOR SELECT TO authenticated
  USING (EXISTS (SELECT 1 FROM documents d
                 WHERE d.id = topics.document_id AND d.user_id = auth.uid()));
-- Writes to derived tables are performed only by the backend role; no INSERT/UPDATE
-- policy is granted to `authenticated` for topics, keywords, topic_clusters,
-- topic_relationships, generated_questions.
-- Storage: bucket `documents` is private; policy allows access only to
-- objects whose first path segment equals auth.uid()::text.

7. Data Retention and Privacy
Data
Retention
Documents and derived results
Kept until the user deletes them; optional expires_at (Settings: keep 30, 90, 180
days or forever). Default 180 days for new documents. A daily job deletes expired
rows.
Stored PDFs
Same as parent document; deleted with it.
Failed analysis runs
Deleted after 30 days.
Study sessions
Kept with the document; deleted on cascade.
Logs
No document content; retained 30 days.
Anonymous MVP usage
No content stored server-side; in-memory cache entries expire within 1 hour.
Account deletion
Immediate hard delete of all user data, completed within 24 hours including
backups purge policy of the provider.

9. Acceptance Criteria
 1. Alembic upgrade from empty to head succeeds; downgrade to base succeeds.
2. A user cannot read another user's rows using the anon key or a different user's JWT (verified by
tests).
3. Deleting a document removes all rows in dependent tables and the storage object.
4. Inserting a topic with score 101, priority URGENT, or depth 5 fails.
5. The Phase 2 API can persist and reload any Analysis Result without loss of fields.
